## 当前调用链 / 数据流

当前仓库没有既有业务调用链。基于需求，目标系统应包含两条核心数据流：

1. 文档处理数据流：上传文件 -> 文件存储 -> 元数据入库 -> MQ 解析任务 -> 文档解析 -> 文本清洗 -> Chunk 切分 -> Embedding -> 向量索引 -> 关键词索引 -> 状态更新。
2. RAG 问答数据流：用户提问 -> 鉴权 -> 会话上下文 -> Query Rewrite -> 向量 / 关键词混合检索 -> 权限过滤 -> Rerank -> Prompt 组装 -> LLM Gateway -> 流式回答 -> 引用和用量落库 -> 反馈评估。

## 现有模块边界与约束

- 未来代码需遵守 `com.lnzz.*` 包命名建议。
- Controller 只能处理 HTTP 入参、校验和调用 Service，不能写核心业务。
- Service 必须 interface + impl，写操作事务边界在 Service impl。
- DAO 只负责数据访问，禁止业务逻辑。
- API 必须使用 `/api/v1/` RESTful 风格，统一返回结构。
- 数据库表、字段采用 snake_case，业务表包含审计字段、软删除、状态、索引和租户隔离字段。
- 日志必须包含 traceId、tenantId、userId、bizId、operation、costMs 等可追踪字段，敏感信息脱敏。

# 方案候选

## 方案 A：模块化单体优先，生产按能力拆分

- 改动范围：一个 Spring Boot 主工程中按领域包拆分 auth、tenant、knowledgebase、document、retrieval、chat、llm、prompt、audit、feedback 等模块；基础设施通过接口抽象向量库、模型供应商和解析器。
- 优点：适合个人 8 周 MVP；事务和调试简单；部署成本低；模块边界清晰后可平滑拆服务。
- 缺点：高并发和大规模文档处理时，问答和解析共享进程可能互相影响。
- 风险：如果一开始模块边界不清，后续拆分成本会上升。
- 迁移成本：中等；需要从模块内接口抽出 RPC / MQ 边界。
- 测试成本：中等；可先用单元测试、集成测试和少量端到端验证覆盖。

## 方案 B：生产级微服务先行

- 改动范围：从第一天拆分用户权限服务、知识库服务、文档服务、解析服务、向量化服务、检索服务、问答服务、模型网关、反馈服务和审计服务。
- 优点：服务职责独立；可按负载水平扩展；更接近大型企业平台形态。
- 缺点：个人开发复杂度高；服务治理、配置中心、链路追踪、分布式事务和部署成本显著增加。
- 风险：MVP 可能被基础设施拖慢，核心 RAG 能力无法按期闭环。
- 迁移成本：低到中等；但初始工程成本高。
- 测试成本：高；需要契约测试、集成环境和服务间调用验证。

## 方案 C：业务代码直接调用模型 API + 只做向量检索

- 改动范围：问答 Service 内直接调用 OpenAI / DeepSeek 等模型 API；文档处理仅做简单 Chunk 和向量入库。
- 优点：实现最快，Demo 成本低。
- 缺点：模型供应商切换困难；Token、成本、限流、审计、重试、熔断和安全策略散落业务代码；难以支持企业治理。
- 风险：一旦接入多个业务场景，维护成本和安全风险快速放大。
- 迁移成本：高；后续需要从业务代码中剥离模型调用、Prompt 和日志。
- 测试成本：低到中等，但覆盖不了企业级治理风险。

# 推荐方案

推荐方案 A。

选择理由：

1. 用户目标包含学习、开发、简历和面试，模块化单体最适合 8 周个人 MVP 闭环。
2. 模块化单体不等于无架构，仍可通过包边界、接口抽象、领域服务和 MQ 异步化保留生产演进空间。
3. RAG 项目早期最大风险不是服务拆分不足，而是文档解析、检索效果、权限过滤、Prompt 治理和评估闭环不足。
4. 生产阶段再根据真实 QPS、文档量、任务堆积和模型调用耗时拆分服务，更符合演进式架构。

关键假设：

- 个人 MVP 以功能闭环和架构清晰为优先。
- 主数据库已由用户确认为 MySQL 8.0；向量检索不放在 MySQL 内硬做，MVP 即采用 Milvus / Qdrant 作为独立 Vector Store。
- 文档规模起步不超过百万级 Chunk；若超过，应重点评估 Milvus / Qdrant 的分片、索引参数和资源隔离。
- 企业暂未强制要求第一阶段微服务化或 Kubernetes 高可用。

# 不采用方案及原因

不采用方案 B 作为 MVP 起点：它虽然生产形态完整，但会让个人开发者在 8 周内过早投入服务治理、部署和联调，降低核心 RAG 能力交付概率。

不采用方案 C 作为企业级方案：它只能支撑 Demo，无法满足模型治理、成本统计、审计、安全隔离和供应商切换要求。

# 风险反证

以下现象出现时，说明推荐方案 A 需要提前向方案 B 演进：

- 文档解析任务大量堆积，影响在线问答响应。
- 单体服务 CPU / 内存受解析、Embedding、Rerank 或流式回答互相争抢。
- 多租户流量差异明显，需要按租户或业务线隔离资源。
- 模型调用统一治理需求增强，如配额、熔断、审计、成本分摊需要平台化。
- Milvus / Qdrant 集群资源不足，召回延迟或索引维护不可接受。

# 降级与回滚

- 模型降级：主模型失败时切换备用供应商或本地模型；无法生成时返回检索摘要和引用。
- 检索降级：Rerank 服务不可用时退回混合检索分数排序；向量库不可用时退回关键词搜索。
- 文档处理降级：大文件进入低优先级队列；解析失败记录原因并支持重试。
- 成本降级：超过租户预算后限制高成本模型、降低 TopK、关闭 Multi Query。
- 部署回滚：MVP 使用 Docker Compose 可按镜像版本回滚；生产使用灰度和蓝绿发布。

# 跨层一致性检查

| 层面 | 一致性结论 |
| --- | --- |
| 架构 | 模块化单体和未来微服务拆分边界一致，先通过领域包与接口隔离能力 |
| API | API 统一 `/api/v1/`，围绕知识库、文档、问答、会话、反馈、模型、Prompt 和统计设计 |
| 数据 | 所有核心表带 `tenant_id`、软删除、审计字段，支持权限过滤和追踪 |
| Prompt | Prompt 配置化、版本化，输入输出契约和安全规则可被测试 |
| 测试 | MVP 先做单元、集成、接口、Prompt Golden Case 和文档处理回归；生产补压测和评测集 |
| 安全 | 检索前、检索中、生成前和引用返回前均需权限校验，避免单点过滤失效 |
