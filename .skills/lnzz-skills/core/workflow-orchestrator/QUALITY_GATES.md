# QUALITY_GATES.md

## 目的

定义 core 主流程的阶段质量门禁，避免“文档已生成但信息密度不足”。

workflow-orchestrator 在路由阶段必须引用本文件进行通过/阻断判断；各 core skill 在输出前也应自检对应门禁。

------

## 1. 复杂度分层

| 层级 | 场景 | 必需门禁 |
|---|---|---|
| L1 简单任务 | 文案、注释、小配置、低风险单点改动 | 目标、范围、验证方式、Next Prompt Handoff（轻量可回复内给出） |
| L2 标准任务 | 单模块功能、普通 Bug、测试补充 | Spec、TODO、Test、Review、Next Prompt Handoff |
| L3 复杂/高风险任务 | 架构、接口、数据、权限、核心业务、重构、优化、Prompt 体系 | Design Research、Design、Prompt（如适用）、Plan、TDD、Architecture Check、Next Prompt Handoff |
| L4 长期/跨模块任务 | 多模块、长期项目、平台能力、规则治理、AI 推理链路 | L3 全部门禁 + PROJECT_REGISTRY + CURRENT_FOCUS + NEXT_PROMPT |

L1 可豁免完整文档，但必须说明不适用原因和替代验证方式。

------

## 2. Spec Gate

进入设计前必须确认：

- 有业务目标，不只写“实现什么”。
- 有使用场景：角色、入口、条件。
- 有功能规则：输入、输出、状态变化、异常路径、边界条件。
- 有非功能要求：性能、安全、权限、兼容、可观测、降级。
- 有可测试验收标准。
- 明确不包含范围。
- 区分事实、假设和待确认问题。

阻断条件：

- 验收标准不可测试。
- 关键规则只存在于会话上下文。
- 待确认问题会影响架构或接口设计。

------

## 3. Design Research Gate

进入 `system-architect` 前，L3/L4 或高风险任务必须确认：

- 读取了现有代码、配置、SQL、测试或历史文档。
- 描述了当前调用链、数据流、状态流或模块边界。
- 至少 2 个可行方案。
- 每个方案有改动范围、优缺点、风险、迁移成本、测试成本。
- 有推荐方案和选择理由。
- 有不采用方案和拒绝原因。
- 有风险反证和降级/回滚路径。
- 检查架构、API、数据、测试是否一致。

阻断条件：

- 没有现状证据。
- 没有方案对比。
- 没有不采用方案。
- 方案会污染模块边界但未说明风险。

------

## 4. Prompt Gate

涉及 Prompt 体系、规则治理、AI 推理链路、模型输出契约或可复用提示词模板时，进入 `task-planner` 前必须确认：

- 有 `PROMPT_SPEC.md`，或明确记录 Prompt Gate 不适用原因。
- 有 Prompt ID、名称、所属能力、调用入口、影响范围和版本。
- 有业务目标、适用场景和不适用场景。
- 有输入契约：变量名、类型、来源、必填、默认值、脱敏要求和约束说明。
- 有输出契约：输出格式、字段说明、错误输出和禁止输出。
- 有 Prompt 模板：角色、任务、上下文、约束、输出格式和失败处理。
- 有规则优先级：系统规则、业务规则、用户输入、上下文资料和模型推断之间的优先级。
- 有安全治理：Prompt Injection、防敏感信息泄漏、危险操作约束、幻觉和不确定性处理。
- 有示例集：正例、反例、边界例、对抗例。
- 有评估方案：Golden Case、回归 Case、评分维度和人工验收路径。
- 有版本、兼容和回滚策略。

阻断条件：

- 只有 Prompt 正文，没有输入/输出契约。
- 没有评估用例或验收标准。
- 没有说明失败、低置信度或不可判断时的输出策略。
- 没有说明规则优先级，导致用户输入可能覆盖系统规则或业务规则。
- Prompt 输出可影响业务决策，但没有说明是否允许推翻规则基线。
- Prompt 正文散落在业务代码中且无系统内置兜底说明。

------

## 5. Plan Gate

进入 `test-designer` 前必须确认每个 TASK 至少包含：

- 需求来源：FR / AC / 澄清项。
- 设计来源：设计章节、方案决策、API 或数据约束。
- 变更位置：模块、包、文件、类、接口、SQL、页面或脚本。
- 前置依赖。
- 实现步骤。
- 测试策略：测试文件、测试命令、预期 RED/GREEN。
- 验收标准。
- 风险与回滚。
- 状态。

阻断条件：

- 只有标题，没有文件路径和测试策略。
- 没有关联需求或设计来源。
- 没有验收标准。
- 多个独立目标混在一个 TASK。

------

## 6. TDD Gate

进入 `spec-driven-coder` 前必须确认：

- 当前 TASK 明确预期行为、修改范围、需求来源和设计来源。
- 已有对应测试文件或复现脚本。
- 已运行测试并记录 RED 失败原因，且失败原因符合预期。
- 若无法测试先行，必须在 TODO 或 TESTPLAN 中说明豁免原因和替代验证方式。

阻断条件：

- 未写测试或复现脚本就准备实现。
- RED 失败原因不是目标行为缺失。
- 测试只验证 mock 或实现细节，不能证明行为。
- 测试豁免没有记录原因。

------

## 7. Implementation Gate

实现阶段必须确认：

- 一次只实现一个 TASK。
- 不新增未设计功能。
- 不扩大模块边界。
- 修改范围与 TODO 一致。
- 异常路径和降级策略符合设计。
- 实现后更新任务状态和实现说明。

阻断条件：

- 实现发现需求或设计冲突。
- 需要跨模块扩大修改但 TODO 未覆盖。
- 为了通过测试破坏架构边界。

------

## 8. Review Gate

进入发布检查前必须确认：

- 测试报告已记录执行命令、结果和失败项。
- 代码审查检查需求符合性、架构边界、测试覆盖、安全、性能、兼容性。
- 高优先级缺陷已关闭，或记录风险接受结论。
- 文档已同步当前真实状态。

阻断条件：

- 隐藏测试失败。
- REVIEW.md 未检查关键设计假设。
- BUG_REPORT.md 中阻断发布问题未关闭。

------

## 9. Release Gate

发布前必须确认：

- 发布范围清晰。
- 已完成项和未完成项清晰。
- 已知风险和回滚方案清晰。
- 发布后观察建议清晰。
- 对高风险未关闭问题明确写出“不建议发布”。

阻断条件：

- 高风险问题未关闭且无风险接受结论。
- 没有回滚或降级路径。
- 关键验证未执行且未说明原因。

------

## 10. Next Prompt Handoff Gate

每次工程任务对话结束前、每个 TASK 阶段性完成后、发布或知识沉淀前必须确认：

- 已读取当前任务目录中的 `STATUS.md`、`CURRENT_FOCUS.md`、`NEXT_PROMPT.md`（如存在）和 `PROJECT_REGISTRY.md`。
- 已基于真实完成事项更新任务级 `00_meta/NEXT_PROMPT.md`。
- 已基于最近活跃任务更新全局 `ai_workspace/NEXT_CONVERSATION_PROMPT.md`。
- 模板包含任务归属、当前阶段、最近完成事项、下一步动作、必读文件、当前质量门禁和用户可直接发送的提示词。
- 模板中的下一步只指向一个明确 TASK、阶段或门禁，并说明不得跳过的前置检查。
- 模板没有声明未验证完成项，没有隐藏阻断、测试失败或环境限制。
- `NEXT_PROMPT.md`、`CURRENT_FOCUS.md`、`STATUS.md` 和 `PROJECT_REGISTRY.md` 的当前进度不冲突；若冲突，必须修正或记录以哪个文件为准。

阻断条件：

- 工程任务结束前未更新任务级或全局下一次对话模板。
- 模板只有“继续上次任务”等空泛描述。
- 模板与 TODO、测试报告、审查报告或注册表中的真实状态冲突。
- 发布或归档文档未记录 Next Prompt Handoff Gate 结论。
