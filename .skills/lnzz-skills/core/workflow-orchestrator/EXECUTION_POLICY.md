# EXECUTION_POLICY.md

## 目的

定义 workflow-orchestrator 在任务执行时的策略控制规则。

用于决定：

- 是否自动执行
- 是否分阶段执行
- 是否需要用户确认
- 是否暂停等待输入
- 是否允许进入下一阶段质量门禁

------

## 1. 执行模式定义

### 1.1 自动执行（AUTO）

AI 可直接连续执行多个阶段，无需用户确认。

适用于：

- 小范围改动
- 单模块任务
- 低风险操作
- 明确需求任务

------

### 1.2 分阶段执行（STEP）

AI 每完成一个阶段后暂停，等待用户确认。

适用于：

- 新功能开发
- 中等复杂度任务
- 需求存在一定不确定性

------

### 1.3 强制确认（CONFIRM）

AI 必须在关键节点暂停，等待用户明确确认后才能继续。

适用于：

- 高风险任务
- 架构变更
- 数据模型变更
- 接口协议变更
- 发布操作

------

### 1.4 观察模式（PLAN ONLY）

只输出计划，不执行。

适用于：

- 用户明确要求方案
- 设计评审
- 技术选型讨论

------

## 2. 默认执行策略

| 任务类型         | 执行模式  |
| ---------------- | --------- |
| 新功能开发       | STEP      |
| Bug 修复（简单） | AUTO      |
| Bug 修复（复杂） | STEP      |
| 设计补充         | PLAN ONLY |
| 设计研究         | PLAN ONLY |
| 测试补充         | AUTO      |
| 发布检查         | CONFIRM   |

------

## 3. 风险识别规则

### 高风险任务

满足任一条件即为高风险：

- 涉及多个模块
- 涉及公共模块
- 涉及数据库变更
- 涉及接口协议变更
- 涉及网关 / 鉴权
- 涉及 Prompt 体系、规则治理或 AI 推理链路
- 涉及核心业务逻辑

### 行为

高风险任务必须：

```text
执行模式 = CONFIRM
```

------

## 4. 执行策略决策流程

workflow-orchestrator 必须按以下顺序决策：

```text
1. 识别任务类型
2. 判断复杂度
3. 判断风险级别
4. 判断质量门禁
5. 选择执行模式
```

复杂度判定必须参考 `QUALITY_GATES.md`。

------

## 4.1 复杂度与执行模式覆盖规则

| 复杂度 | 默认执行模式 | 控制要求 |
|---|---|---|
| L1 | AUTO | 可轻量文档，但必须说明验证方式 |
| L2 | STEP | 阶段产物齐全后继续 |
| L3 | CONFIRM | design-researcher 与设计完成后暂停确认 |
| L4 | CONFIRM | 额外维护 PROJECT_REGISTRY 与 CURRENT_FOCUS |

高风险任务无论原始类型如何，执行模式必须提升为 CONFIRM。

------

## 5. 执行控制规则

### AUTO 模式

- 自动推进多个阶段
- 不跳过流程
- 必须记录所有产物
- 不允许跳过 TDD Gate；若豁免测试先行，必须记录原因

------

### STEP 模式

每个阶段必须：

输出：

- 当前阶段
- 阶段产物
- 完成情况
- 下一步计划

并等待：

👉 用户确认后再继续

------

### CONFIRM 模式

必须在以下节点暂停：

- 需求确认后
- 设计完成后
- 编码前
- 发布前

必须输出：

- 风险说明
- 影响范围
- 回滚方案（如适用）

------

### PLAN ONLY 模式

- 只输出完整流程和方案
- 不执行任何代码操作
- 默认不修改业务代码
- 若用户明确要求生成或更新设计/计划文档，可只修改任务文档，不进入实现

------

## 6. Superpowers 与执行策略结合规则

### AUTO

允许使用：

- executing-plans
- test-driven-development

------

### STEP

推荐使用：

- writing-plans
- brainstorming
- test-driven-development（进入实现前）

------

### CONFIRM

必须使用：

- verification-before-completion
- brainstorming（复杂设计研究适用）

------

### 并行执行限制

使用以下 skill 时：

- dispatching-parallel-agents
- subagent-driven-development

必须满足：

- 已完成依赖分析
- 执行模式至少为 STEP

------

## 7. 强制中断条件

出现以下情况必须停止执行：

- 需求不明确
- 设计缺失
- TODO.md 未完成
- Plan Gate 不通过
- TDD Gate 不通过
- 测试失败
- 存在高风险未评估
- design-researcher 门禁结论为阻断或回退需求澄清

------
